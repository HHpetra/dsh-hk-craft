## ADR-0001 — 插件装入现有 dsh profile，不建独立启动入口

**背景**：dsh 插件模板默认走“产品专属 `DSH_HOME` + 独立 profile + launcher/桌面壳”的形态（模板 ADR-0001、ADR-0003）。本项目需求明确相反：它是 dsh 自身的插件，完全在 dsh 内使用，不封装成另一个启动界面。

**决策**：

- 交付物是一个 **dsh bundle**，通过 dsh 的 **Plugins → Add plugin → 本地目录** 装入用户已有的 `desktop` profile。
- `desktop` profile 由 Electron 应用独占管理，CLI 的 `dsh plugin --profile desktop ...` 被上游明确拒绝；安装/卸载必须走应用内插件面板。
- 不创建 `apps/launcher`、Electron/Tauri 外壳，不建产品专属 `DSH_HOME`、独立 profile 或独立端口。
- 安装只增加 profile 的依赖与 `dsh.profile.bundles` 条目；卸载可逆。
- 插件装载发生在用户下次启动 dsh 时，沿用其现有 Web UI。

**后果**：

- 仓库没有 `apps/` 与 `packages/dsh-profile/`；模板中这两部分被本决策取代。
- 端口、home、会话数据、登录态都归用户现有 dsh 管理，本项目不碰。
- 验证链改为“安装到 `desktop` → 重启 dsh → 卸载”，而不是启动本项目自己的进程。

## ADR-0002 — 一个 bundle 包承载 host 与 client 两面

**背景**：dsh 的插件行既可提供宿主服务，也可通过 `dsh.client` 声明浏览器侧入口。拆成多个包会让安装、版本与 patch 行变复杂。

**决策**：

- `packages/dsh-hk-craft` 同时承载 host 入口与后续的 client UI。
- `dsh.bundle.patch` 指向唯一 patch；host 面由该包的 `main` 提供。
- 需要浏览器 UI 时，在同一个 `package.json` 增加 `dsh.client`，构建 `lib/client.js`，并在 `exports` 暴露 `./client`。
- 客户端 bundle 采用 dsh Web 壳的 `window.__ModuleLoader__.load({ id, factory })` 格式；入口 id 与 patch 行 `name` 完全一致。

**后果**：

- 安装/卸载只有一个包、一条 bundle 记录。
- host 与 client 的版本永远同步，不会出现半套升级。
- client 构建必须遵守 dsh 的平台模块 external 约定，不能把 React 等平台模块打进 bundle。

## ADR-0003 — 跟随机器上已安装的 dsh 列车

**背景**：dsh 的插件 API 与包边界仍在快速演进；混用不同列车会破坏 ESM 命名导出与运行期解析。

**决策**：

- 目标运行时以 `desktop` profile 实际加载的 dsh 为准（Desktop 应用内置，当前 `0.2.1-rc.5`），记录在 `deps/VERSIONS.md`；全局 `dsh` CLI 与它可能不是同一列车，不能拿 CLI 的版本判断 `desktop`。
- bundle 用 `engines.dsh` 声明兼容范围；需要 `@deepseek-ai/dsh*` 类型或运行期包时，peer 依赖与 devDependency 使用同一列车版本。
- 升级 dsh 时同步更新版本表、`engines.dsh`、peer 依赖，并重跑安装/启动/卸载冒烟。

**后果**：

- 不 vendor `@deepseek-ai/dsh`，也不在仓库内固定一份独立运行时。
- 插件不能假设比目标版本更新的 API；遇到缺失能力时先记录 ADR 或调研，不 fork 上游。

## ADR-0004 — 唯一包管理器是 pnpm workspace

**背景**：混用 npm / pnpm 锁文件会冲突；dsh 对扁平 `node_modules` 与链接 profile 的解析敏感。

**决策**：

- 根目录 private workspace：`packages/*`。
- 只提交根目录 `pnpm-lock.yaml`；`packageManager` 钉死 pnpm；`preinstall` 拒绝 npm/yarn。
- 只在仓库根 `pnpm install`；子包不单独安装。

**后果**：

- 克隆后第一步永远是根目录 `pnpm install`。
- 本地安装到 profile 的是链接包，保留本仓库自己的 `node_modules`。

## ADR-0005 — 首个能力：多会话分屏 + 侧栏精简（窗格 ⇄ 会话 1:1）

**背景**：重度用户同时开多个项目、多个对话。dsh 把「工作区 + 其下全部对话」平铺在一个侧栏里，对话一多整列就不可用；同时 dsh 一个窗口只有一个主对话视图，需要并排对照时只能来回切换。需求于是收敛为三件事：侧栏只留工作区名与状态灯、用 `/resume` 与 `/clear` 替代侧栏对话列表、主区域支持 VS Code 式任意分割。

**决策**：

1. **接管主区域，而不是覆盖它**：注册 `main` 键控槽（key `hkcraft.panes`）并调 `ctx.layout.selectPanel(...)`。`main` 的渲染键是 `activePanelId ?? "conversation"`，切过去时原生对话面板会**卸载**，因此不会出现双挂 composer 或双份流式输出。
2. **每个窗格 = 一个会话**，窗格是会话的显示槽而不是可空容器；关窗格即「取消当前回合并释放客户端引用」，会话数据保留、可经 `/resume` 重新拉回。切换工作区只换可见的窗格树，**不关闭**任何会话。
3. **布局是手动分割树**，每个工作区一棵，树上只装本工作区的会话（不做跨工作区同屏）；树形、比例、焦点、每格视图按工作区落盘。
4. **标签条是窗格的索引**，不是第二层容器；`对话 / 轨迹` 是窗格内的分段开关，按窗格记忆。这样"哪个会话"和"哪种视图"两个维度不会互相冒充。
5. **侧栏工作区区块整块替换**：以更低 `priority` 覆盖 `sidebar.workspaces` 这个 `single` 槽，只保留「名称 + 三态灯 + 添加工作区」，其余侧栏部件不动。
6. **命令是纯客户端的**：`/clear`、`/resume` 经 `commandUi` 注册，走壳提供的 `popupSelect` 选择器，不发给模型。
7. **渲染指定会话的对话**：窗格声明一个 `scope: "session"` 子槽拿到壳给的 `SessionProvider`，再以 `renderFactorySlot("conversation.content")` 挂载完整对话；焦点窗格独占 `mainView` 引用以维持 dsh 对"当前会话"的单值推导。

**后果 / 约束**：

- 分屏依赖 `conversation.content` 这个**字符串 Factory 名**与单值 `mainView` 推导。上游若改名或改动推导，只需修适配层（`dsh-pane-host.js`），但要锁 `engines.dsh` 并在升级时重跑冒烟。
- 跨工作区不能同屏；跨项目找历史要先切工作区。这是用"布局简单"换"信息可见性"的自觉选择。
- 刷新或重启后恢复树形、比例、焦点与视图，但**不恢复滚动位置与未发送草稿**；由外层界面触发的原生会话揭示会卸载分屏面板。
- 侧栏区块内搜索随精简一并移除（`Mod+K`、`Mod+O` 因此变为空操作）；若"找不到旧对话"成为高频抱怨，再以全局搜索面板补回。
- `lib/client.js` 由 esbuild 生成、不入库；构建脚本在受限沙箱里会回退到 esbuild CLI，两条路径产出必须一致。

## ADR-0006 — 新会话按会话数量均分横排；窗格工具栏只留视图切换与关闭

**取代关系**：本 ADR 取代 ADR-0005 的**决策 3**（布局是手动分割树、比例由用户拖拽决定）和**决策 4** 中「`对话 / 轨迹` 是窗格内分段开关」的形态；ADR-0005 的其余决策（接管主区域、每窗格一个会话、标签条只是索引、侧栏替换、纯客户端命令等）继续有效。

**背景**：ADR-0005 的窗格是 VS Code 式的任意分割树，`+` 会在焦点窗格里再做一次 50/50 分割。实际使用中，第三个会话常常得到「四分之一 + 四分之一 + 一半」的宽度，且新窗格出现在最后一个窗格内部，和「再开一个会话」的预期不符。同时，窗格头部的 `⋯` 菜单把向右、向下分割和关闭混在一起，用户希望头部只保留关闭，并增加一个对话 ⇄ 轨迹的切换按钮；纵向分割暂不需要。

**决策**：

1. **窗格头部只保留两个动作**：一个 `对话 ⇄ 轨迹` 切换按钮（单按钮，标签写「将切换到的视图」）和一个关闭按钮。`⋯` 菜单、分割与关闭的菜单项一并移除。分割仍可通过键盘 `Ctrl+Shift+E`（向右）触发。
2. **`+` 按会话数量均分**：在焦点窗格之后插入新窗格，然后把整棵布局树重建为一排等宽列（平衡二叉树，每个分裂节点的比例等于左子树叶子数 / 总数），新窗格获得焦点。空工作区仍直接打开第一格。
3. **暂停纵向分割**：删除 `Ctrl+Shift+D` 与所有向下分割入口；布局树与几何仍能读取旧的 `col` 节点（兼容已保存布局），但任何新操作都不会再产生纵向分割。下一次 `+` 会把整棵树重排为横排。
4. **视图切换仍受 `developerTools` 门控**：该开关关闭时不渲染轨迹视图，按钮随之隐藏（与原生 dsh 一致，仍不做 disabled 视图）。

**后果 / 约束**：

- 每次 `+` 都会丢弃用户手动拖出的比例；这是「按数量均分」的直接代价。关闭窗格仍沿用“兄弟子树提升”，不会重新均分，因此 `+` 与关闭后的宽度可以不同。
- 窗格头部的按钮数量固定为两个；将来若要恢复纵向分割，需要新的手势/菜单和明确的迁移策略，而不是把 `⋯` 菜单原样加回来。
- 视图渲染由**窗格布局记录**驱动：窗格的 embedded occurrence 覆盖 `conversation.content` 的 `views` 本地插槽，把布局里的视图作为 `conversation.session` 的 `view` 属性传入，不再写 dsh 的 per-session View store。`binding.activate` 仍用于预热数据目标；该接缝记录在 `docs/upstream-contracts.md`。
- 布局仍是纯数据转换（`layout-tree.js` 的 `tile`），不涉及 dsh 上游的 host 契约。

## ADR-0007 — 侧栏工作区管理、窗格条工具栏与设置页搬迁

**背景**：ADR-0005/0006 交付了分屏与精简侧栏，但侧栏工作区只剩“名称 + 三态灯 + 添加”，原生的删除与拖动排序在接管槽位后一起丢失；三态灯也不区分“从未在分屏打开过”和“没有对话在跑”。同时分屏后原生对话头部不再挂载，“当前模式”和“子代理查看”两个入口消失，诊断与分屏切换两个开发期按钮常驻侧栏 footer，`+` 又被右对齐到远端。本 ADR 记录这一轮补齐的管理与工具栏形态。

**取代关系**：本 ADR 取代 **ADR-0005 决策 5** 中“只保留「名称 + 三态灯 + 添加工作区」”的描述（三态灯改为四态灯，并补回删除与拖动排序）。ADR-0006 原样保留、继续有效。

**决策**：

1. **侧栏工作区管理回到插件侧栏**：
   - 灯改为 `gray | green | yellow | red` 四态，优先级 红 > 黄 > 绿 > 灰。**灰 = 未启用（从未在分屏打开过）或已启用但没有一段对话真正结束（会话全是空白）**。绿只表示“至少一段对话结束且当前空闲”，黄表示有会话运行中，红表示有会话等待用户操作（审批 / 提问 / 计划确认）。不设“错误灯”，因为 dsh 没有可靠的“上一回合失败”字段。
   - “启用”只由窗格布局推断：已加载的布局，或插件自己的布局键 `dsh.hkcraft.layout.v1.<workspaceId>`。在原生视图打开工作区不算启用；删除工作区时清掉布局键。
   - 工作区行提供**删除**入口：先二次确认，再调公开的 `workspaces.delete(id)`，成功后由窗格控制器清理布局并释放窗格引用；**不中断**其中正在运行的会话，也不删目录、会话或未分组数据。允许删除最后一个工作区，焦点落到下一行，否则落到“添加工作区”。
   - 工作区行支持**指针拖动排序**（移动超过 6px 才进入拖动），落点换算成公开的 `workspaces.insertBefore(sourceId, beforeWorkspaceId?)`；**Host 是顺序唯一真源**，侧栏不本地排序、不缓存顺序，失败只显示 Host 的已提交顺序。
2. **临时控件搬进 HK Craft 设置页**：删除 `sidebar.footer.action` 的诊断与分屏切换注册，改为 `settings.section` 贡献一个“HK Craft”页，内联诊断信息并提供过渡的“进入 / 退出分屏”开关；成功后关闭设置页，失败显示原因。设置页只依赖槽、locale 与窗格控制器闭包，缺少设置服务时整体不注册。
3. **窗格条工具栏承载原生头部能力**：
   - 标签条分三层：外层条、可滚动视口（`tablist` + 紧贴最后标签的 `+`）、视口之外不参与滚动的右侧操作组。`+` 不再右对齐，标签先截断，右侧组不收缩。
   - 右侧原生组按原生头部的相对顺序提供**只读当前模式**与**子代理查看**；两者共用右侧组，为以后的原生工具预留位置。
   - **本版不提供“打开右侧边栏”**：上游 `rightbar` 只在 `activePanelId === null` 时可见，分屏面板激活时原生右侧栏被隐藏且公开服务拿不到“当前会话”，没有可靠的打开路径。以后若上游提供接缝，再单独立项。
4. **上游契约与文档落点**：新增能力（`workspaces.delete`、`workspaces.insertBefore`、`settings.section`、Agent 预设名册、子代理目录）记录在 `docs/upstream-contracts.md`；插件内部的“启用”与四态灯定义记录在 `docs/README.md` 与本 ADR，不写进上游契约页。

**后果 / 约束**：

- 灰灯同时表示“未启用”和“已启用但没有结束过对话”；这是“未启用用灰”与“只有真正结束才绿”两条要求的唯一自洽解。若将来需要第五态，另立决策。
- 失败结束的回合仍是绿：上游没有失败位，插件不假装知道。
- 删除不中断与“关闭窗格会中断当前回合”刻意不同，确认弹窗必须写清边界。
- 侧栏只渲染工作区行，不显示 dsh 的“未分组”，因此删除后会话在原生侧栏可见、在本插件侧栏不可见。
- 本版排序只做指针拖动（无键盘替代）；子代理只列直接子会话，不做嵌套、悬停展开、失败重试或父级面包屑。
- 右侧工具栏与设置页依赖上游槽位；升级 dsh 时按 `docs/upstream-contracts.md` 复验，缺少可选服务时安静降级。

## ADR-0008 — 五态工作区灯与窗格头部原生控件

**背景**：ADR-0007 的四态灯把“绿”定义为“至少一段对话结束且当前空闲”。重启 dsh 后，只要工作区里有过对话、当前没在跑，就全部变绿，无法区分“一直空闲”和“你离开时有对话刚跑完、还没看”。同时，ADR-0007 把“当前模式”和“子代理查看”放在标签条右侧组，但用户希望它们在每个对话窗格自己的顶部工具栏里，这样并排时每个窗格都能看到自己的模式与子代理。

上游 `sessionStatus` 提供了区分“空闲”和“刚结束未读”的机制：`completionUnread` 在非当前会话由运行转为空闲时置位，在该会话成为当前会话（被聚焦）或再次开始运行时清除（`docs/upstream-contracts.md#completion-unread`）。

**取代关系**：本 ADR 取代 **ADR-0007 决策 1** 的四态灯定义（增加空闲态，绿灯改为未读完成）和 **ADR-0007 决策 3** 的标签条右侧组位置；同时取代 **ADR-0006 决策 1** 中“窗格头部只保留视图切换与关闭两个动作”的约束。ADR-0006 的其余决策（`+` 按会话数量均分、暂停纵向分割等）继续有效。

**决策**：

1. **工作区灯改为五态**：红 > 黄 > 绿 > 蓝（空闲）> 灰。
   - 红：有会话等待用户操作（审批 / 提问 / 计划确认）。
   - 黄：有会话运行中。
   - 绿：至少一个成员有 `completionUnread`（对话刚结束、还没看），且没有运行/等待。
   - 蓝（空闲）：至少一段对话已经开始，且没有运行、等待或未读完成。
   - 灰：未启用（从未在分屏打开过），或已启用但还没有已开始的对话（全是空白会话）。
   - 不设错误灯：dsh 没有可靠的“上一回合失败”字段。
2. **“空闲”与“已结束”分开**：绿灯只给未读完成，不再表示“没有会话在跑”。重启后已空闲的工作区显示蓝灯；后台跑完且未查看的显示绿灯；聚焦该会话后 `completionUnread` 清除，回到蓝灯。
3. **当前模式与子代理移到每个窗格头部**：
   - 每个窗格头部显示自己的标题、只读当前模式、子代理查看、视图切换与关闭；两个控件读该窗格的 `sessionId`，不是焦点窗格。
   - 控件各自按需隐藏（无预设、无直接子会话时不占位）；宽度上限 140 / 160 px，标题先截断。
   - 标签条只保留标签与紧贴最后标签的 `+`；删除标签条右侧组及其 seat 注册机制（`pane-toolbar.js` 不再存在）。
4. **文档落点**：`completionUnread` 的置位/清除规则记录在 `docs/upstream-contracts.md`；五态灯与窗格头部工具栏的 UI 定义记录在 `docs/README.md` 与本 ADR；术语同步到 `GLOSSARY.md`。

**后果 / 约束**：

- 工作区灯依赖 `completionUnread`：该字段只在非当前会话结束后置位；如果上游改变清除时机，绿灯的“未读”语义需要复验。
- 窗格头部在很窄的宽度下会挤占标题；当前用两个宽度上限与标题截断兜底，没有折叠菜单。若并排窗格更窄，后续可以考虑只显示图标或收进菜单。
- 标签条不再承载原生功能，右侧边栏仍因上游隐藏 `rightbar` 而暂缓；未来要加原生工具，应在窗格头部或另立右侧面板，而不是恢复标签条右侧组。
- 删除、拖动排序、设置页与右侧边栏暂缓等 ADR-0007 其余决策继续有效。

## ADR-0009 — 分屏改为 dsh 侧边栏式的局部分栏，并增加可配置的窗格上限

**背景**：ADR-0006 的 `+` 会把整个工作区重排为一排等宽列，新建窗格后所有手动拖出的比例全部丢失，且窗格数量没有上限：开着四五个会话时每一格都窄到不可用。dsh 自己的右侧边栏（`@deepseek-ai/dsh-client-ui-sidebar-right` + `ui-dockkit`）已经有一套成熟的分栏规则：分割只作用于参照窗格，新格是它的等宽兄弟；面（surface）有一个格数预算，预算用尽时禁用分栏控件并给出原因；关闭窗格不会重排其余格子。本 ADR 把主区域分屏改到同一套规则上。

**取代关系**：本 ADR 取代 **ADR-0006 决策 2**（`+` 按会话数量重排整排）和 **ADR-0006 决策 3**（只能由 `+` 重排为横排、比例不保留）中与新建窗格有关的部分；ADR-0006 决策 1（窗格头部动作）与决策 4（视图受 developerTools 门控）继续有效。ADR-0005 的“每窗格一个会话、接管主区域、标签条是索引”等决策继续有效。

**决策**：

1. **局部分栏**：`+`、`Ctrl+Shift+E`、`/resume` 的 Ctrl+Enter 都只分割**焦点窗格**，新窗格是该窗格的等宽右兄弟并获得焦点；其余窗格的位置和拖拽比例保持不变。空工作区仍直接打开第一格，不消耗窗格预算。
2. **窗格上限**：每个工作区默认最多 **4** 格，参考 dockkit 的 `MAX_DOCK_PANES` 与侧边栏“预算用尽即禁用分栏控件”的行为。上限是**用户设置**，可在 HK Craft 设置页改为任意非负整数，`0` 表示**不限制**。
3. **上限只阻止新建**：达到上限时不创建窗格、不创建会话；`+` 保持可见但禁用，并用可聚焦提示说明“已达 N 格上限”。降低上限或恢复一个更宽的旧布局都不会关闭任何窗格；关掉窗格释放名额后才能继续分栏。已经挂载的会话（含“已在窗格中”的 `/resume` 结果）只聚焦、不新增窗格，因此不受上限影响。
4. **设置持久化**：上限写在 origin 级 `dsh.hkcraft.settings.v1`（`{ version: 1, maxPanes }`），与按工作区存放的布局键分开；读失败或值非法回落到默认 4。设置修改立即作用于已打开的面板，不重载布局。
5. **纵向分割仍暂停**：新操作只产生 `row` 分割，旧的 `col` 节点仍可读取和拖拽；这保持 ADR-0006 决策 3 的现状。

**后果 / 约束**：

- 每次 `+` 只影响焦点窗格所在的一支，不再有机会“顺手”均衡整排；用户可用分隔条把某一格拖大，这是有意的。
- 上限按工作区独立计算，不是全局会话数；不同工作区各自可以开满自己的格子。
- 分栏规则在插件内实现（`layout-tree.js` 的 `split` 与 `pane-budget.js`），**不 import** `@deepseek-ai/dsh-client-ui-dockkit`：该包是 dsh Web 壳的内部引擎，不在插件可用的平台模块里。
- 上限为 0 时 UI 不会显示预算原因；窗口再宽也受浏览器布局与最小格宽约束，插件不额外做像素门槛（dsh 侧边栏的 `halvesFit` 规则未移植）。
- 设置只存在浏览器 `localStorage`，不写入 profile 或 `cordis.patch.yml`；换 profile / 换 origin 不共享。
- 侧栏的“子代理查看 / 在新窗格打开”同样经过控制器，因此达到上限时会失败（`false`），由控制器快照的 `error` 记录原因；不自动关掉别的窗格来腾位置。

## ADR-0010 — 创建进行中的分栏与空工作区第一格

**背景**：ADR-0009 规定上限只阻止新建，降低上限不关闭已有窗格。会话创建要往返一次，这中间会出现三类交叉：分栏已经通过检查时用户把上限调低；空工作区第一格还在创建时再次按「新会话」；同一等待期间用户打开了别的会话或切到别的工作区。不规定这三类，界面会多开窗格、留下没人用的空会话，或把新会话写进用户已经离开的布局。

**取代关系**：本 ADR 不取代 ADR-0009。局部分栏、默认 4 格、`0` 不限制、上限只阻止新建、按工作区计算、不 import 内部停靠套件，都继续有效。本 ADR 只补充「上限只阻止新建」在创建进行中的边界。

**决策**：

1. **已占名额的分栏继续落地**：分栏已经通过预算检查并占住名额后，即使用户在会话创建返回之前把上限调低，这一次仍然落地，不取消创建，也不关闭窗格。之后的新分栏才按新上限判断。因此短时间内窗格数可以比刚保存的上限多出正在创建的那几格，与超限旧布局仍可显示同一类。
2. **空工作区的快捷键**：没有焦点窗格时 `Ctrl+Shift+E` 无操作。第一格由 `+` 和 `/resume` 的 Ctrl+Enter 打开，不消耗分屏预算。
3. **空工作区的重叠新建**：第一格的会话还在创建时，再次触发「新会话」（空状态按钮、`Ctrl+Shift+N`、没有焦点窗格时的 `+`）直接忽略，不再创建会话。第一格出现之后，`Ctrl+Shift+N` 仍在焦点窗格里新开一段，`+` 仍在旁边分栏。
4. **第一格只落在原工作区**：该会话创建返回时，只在当初那个工作区仍然没有窗格时写入第一格，并且不把可见工作区切回去。如果那个工作区已经有窗格，不替换焦点窗格，也不再分栏；已经创建出来的会话留在历史里。
5. **设置写入失败**：写入失败不抛错，不回滚内存中的上限；设置页显示失败原因。读失败或值非法仍按 ADR-0009 回落到默认 4。

**后果 / 约束**：

- 进行中的分栏会占住名额，标签条的 `+` 在这一格落地前就按已满处理。
- 被忽略的第二次「新会话」不会留下空会话。用户抢先打开别的会话时，已经创建成功的那一次没有取消接口，所以留在历史里、不放进窗格。
- 第一格的落地不跟随可见工作区。用户切走之后，新会话只出现在原来那个工作区。

## ADR-0011 — 新建横向分栏按当前窗格数均分宽度

**背景**：ADR-0009 把新建分栏改成只把焦点窗格一分为二，其余格子的宽度不动。连续在新窗格上再分时，宽度变成 1/2、1/4、1/8，最后一个窗格只分到剩余的一半。实际使用希望新建之后整行按当前窗格数等宽。

**取代关系**：本 ADR 取代 **ADR-0009 决策 1** 中「新窗格是焦点窗格的等宽兄弟，其余窗格的拖拽比例保持不变」。新窗格仍然插在焦点窗格右侧，叶子顺序不重排。ADR-0009 的窗格上限、ADR-0010 的创建中边界、纵向分割暂停都继续有效。宽度规则部分回到 ADR-0006 决策 2，但不把树重建成平衡二叉树，也不在 `+` 时拆掉已有的纵向分割。

**决策**：

1. **横向新建后均分宽度**：`+`、`Ctrl+Shift+E`、`/resume` 的 Ctrl+Enter 仍把新窗格插在焦点窗格右侧并聚焦。随后每一处 `row` 分割的比例改成「左子树窗格数 / 该分割下的窗格数」，纯横排里每个窗格宽度为 `1 / n`。
2. **拖拽比例让位给这一次均分**：横向新建会丢掉此前拖出的横向比例。关闭窗格仍只提升兄弟子树，不重新均分。分隔条在下一次横向分栏之前仍然有效。
3. **纵向分割不参与均分**：新操作仍只产生 `row`。若调用 `col`，只把参照窗格上下对半，不改已有横向比例。已保存的 `col` 节点保持原样；它在外层横排里按其中的窗格数占宽度，同一列里的窗格共享这一列。
4. **比例地板不变**：比例仍限制在 `[0.1, 0.9]`。默认上限 4 格时 `1/4` 不受影响。某一侧窗格占比低于 0.1 时，该比例会被夹到 0.1，宽度不再严格相等。

**后果 / 约束**：

- 关掉最右侧窗格后，剩下的格子不一定等宽（例如三等分关掉最后一格会留下 1/3 与 2/3）。下一次横向新建才会再次均分。
- 含旧纵向分割的布局在下一次横向新建后，宽度按子树窗格数分配，不会被拆成一排。
- 窗格上限、预算只阻止新建、创建进行中的边界，仍以 ADR-0009 与 ADR-0010 为准。

## ADR-0012 — 桌面通知由渲染进程发送，按五类会话信号区分

**背景**：dsh 没有面向插件的桌面通知能力：`@deepseek-ai/*` 中没有 notification 包或 `ctx.notify`；Electron 主进程只用 `Notification` 发过强制更新提醒，且没有暴露 IPC；客户端里的 `Toast` 是应用内浮层，不是 Windows 通知。插件客户端本来就在 dsh 的 Electron 渲染进程里，`dsh-app://` 是 secure context，主进程的 `installMicrophonePermissions` 对非 `media` 权限默认放行，因此标准 `Notification` API 可以直达 Windows toast。用户已确认按五种类型区分、始终通知、点击后切到对应会话。

**决策**：

1. **纯客户端发送**：通知由 `src/client/notifications.js` 在渲染进程里用 `new Notification(...)` 发出；不新增 host 服务、路由、端口或 IPC，也不改 dsh 主进程。通知设置存在 origin 级 `localStorage["dsh.hkcraft.notifications.v1"]`，不写 profile。
2. **五类信号，不读会话历史**：`approval` / `question` / `plan-review` 来自 `uiSession.sessionStatus.pendingInteraction.kind`；`completed` 是 `running` 由 `true` 变 `false`；`failed` 来自 `remote.$on("api-session/error")`。失败优先于紧随其后的完成；子代理会话（`origin === "subagent"`）不单独通知，等父会话结束。
3. **始终通知**：不做前台/后台门槛；dsh 在前台时也发系统通知。初始订阅只建立基线，不回放历史状态。
4. **点击回到会话**：先聚焦窗口；分屏面板激活时已打开的会话聚焦所在窗格、未打开的在焦点窗格右侧新开（受窗格上限约束）；原生视图调用 `uiWorkspace.openSession`。
5. **通知身份与降级**：等待类用 `requireInteraction` 与 `renotify`，完成/失败不常驻；按 `type + sessionId` 打 `tag`，同一会话同一类型的新通知替换旧的。`Notification` 缺失、权限被拒或构造失败时静默降级，设置页显示原因并提供“发送测试通知”。
6. **设置页承载开关**：总开关、五类开关、声音、权限状态、测试按钮都在 HK Craft 设置页；类型文案随 locale 切换。

**后果 / 约束**：

- Windows toast 的应用身份取决于 Electron 进程的 AUMID 与开始菜单快捷方式；安装包的快捷方式 AUMID 是 `com.deepseek.dsh`，而应用代码没有显式调用 `setAppUserModelId`。首轮实机必须用设置页的“发送测试通知”验证；如果 Windows 不显示，传输层需要换成宿主/原生 helper，但五类信号、文案与点击策略不变。
- 点击只能 `window.focus()`；渲染进程没有还原托盘窗口的公开桥。窗口被隐藏到托盘时，点击通知可能只聚焦而不还原，后续如需还原要上游提供窗口 IPC。
- 通知不改变侧栏五态灯与 `completionUnread` 的语义；关掉通知不影响分屏、侧栏与设置页。
- 新增通知类型（目标、后台任务、调度）需要新的公开信号；不要在客户端读会话历史来推断。

## ADR-0013 — 桌面通知增加“前台可见会话不打扰”选项

**背景**：ADR-0012 按用户当时的选择采用“始终通知”，不做前台/后台门槛。实际使用时，如果 dsh 窗口就在前台、触发通知的对话也正显示在窗口里，系统通知是重复的：用户已经能看到回答或审批面板。用户要求增加一个可选开关，按“该对话是否在焦点窗口里可见”来抑制通知。

**取代关系**：本 ADR 只取代 **ADR-0012 决策 3** 中“始终通知、不做前台/后台门槛”的部分。ADR-0012 的五类信号、失败优先、子代理排除、点击回会话、localStorage 设置与降级策略继续有效。

**决策**：

1. **新增设置 `suppressWhenVisible`**，默认 `false`，保持原有“总是通知”的行为；在 HK Craft 设置页“桌面通知”一节中以独立复选框呈现，总开关关闭时禁用。
2. **抑制判据**：以下两条同时成立才不弹：
   - dsh 窗口在前台：`document.hasFocus() === true` 且 `document.visibilityState !== "hidden"`；
   - 该会话在焦点窗口中可见：
     - 分屏面板激活时，`controller.paneIndexOf(sessionId) != null`。分屏里当前工作区的所有窗格同时可见，因此按“窗口”而不是“焦点窗格”理解：同工作区任一窗格里的对话都算可见；
     - 原生视图下，`mainSessionId(sessions.list) === sessionId`（dsh 的 `mainView` 保留项）。
3. **其它情况仍通知**：会话在其它工作区、dsh 不在前台、窗口隐藏/最小化，或分屏面板未激活且不是原生主对话时，都照常发通知。
4. **作用于五类**：完成、失败、等待授权、等待回答、计划待审阅都受此选项约束；等待类本来就有应用内审批/提问面板，所以抑制不丢失操作入口。
5. **测试通知不受约束**：设置页的“发送测试通知”是诊断动作，继续绕过总开关与前台抑制，用于验证 Windows toast 身份。

**后果 / 约束**：

- 抑制发生在通知产生之前；被抑制的事件不会排队，等 dsh 失焦后再补发。用户已经看到的内容不再补一条旧通知。
- 判据依赖渲染进程的 `document.hasFocus()` 与 `visibilityState`；DevTools 获得焦点、或窗口被其它应用覆盖但 Chromium 仍报告 focused 时，行为以浏览器报告为准。
- 分屏可见性依赖 `paneIndexOf` 的“当前工作区布局”语义；如果未来支持把窗格折叠/隐藏，需要重新定义“可见”。
- 该选项只影响系统通知，不改变五态灯、`completionUnread`、审批/提问面板与点击回会话。

## ADR-0014 — shadow `conversation`，保留原生右侧栏

**背景**：分屏本身是成立的：每个窗格用 `SessionProvider` 和 `conversation.content`（`variant: "embedded"`）渲染真实对话，焦点窗格持有 `mainView`。问题只在接管位置。ADR-0005 决策 1 注册了新的 `main` key `hkcraft.panes` 并调用 `ctx.layout.selectPanel(...)`。上游右侧栏只在 `panelInfo.activePanelId === null` 时可见，并把屏上会话交给 `sidebarRight`。插件面板一旦被选中，右侧栏隐藏，窗格里打开文件会报 `no session surface is mounted`。

**取代关系**：本 ADR 取代 **ADR-0005 决策 1** 中“注册新 `main` key 并 `selectPanel`”的部分。ADR-0005 的其余决策（每窗格一个会话、标签条只是索引、侧栏替换、纯客户端命令等）继续有效。同时取代 **ADR-0007 / ADR-0008** 里“右侧边栏在分屏中不可用、因此不做开关”的限制。ADR-0008 把模式与子代理放进每个窗格头部的决定继续有效。

**决策**：

1. **shadow `conversation`，不 `selectPanel`**：在 `main` 槽注册 `key: "conversation"`、`priority: -1` 的条目，遮住官方 `ConversationPanel`。全程不调用 `ctx.layout.selectPanel`，让 `activePanelId` 保持 `null`。不要用 `selectPanel('conversation')` 冒充回到会话，那会把 `activePanelId` 设成非 null，右侧栏再次隐藏。
2. **焦点窗格继续持有 `mainView`**：右侧栏因此跟随焦点窗格的会话。插件不替换 `rightbar` occupant，不在每个窗格里再挂一份右侧栏。
3. **标签条补一个右侧栏开关**：调用 `ctx.sidebarRight.toggleExpanded()`。服务缺失时不渲染按钮，也不把 `sidebarRight` 放进顶层 `inject`。`isExpanded()` 不可订阅，按钮状态允许短暂不准。
4. **原生 current 跟到焦点窗格**：`uiSession.adapter.current` 变到未打开的会话时，替换焦点窗格的会话；变到已打开的会话时，聚焦那个窗格（必要时先切工作区）。不因此自动新开一格。控制器自己 retain `mainView` 时不递归。
5. **v1 仍是一格也用插件窗格**：不在单窗格时交还原生对话，不渲染原生 header / lineage / hero。关掉最后一个窗格显示空态，不把主区留白。打开设置时右侧栏按原生规则隐藏，返回后 shadow 重新挂上，分屏状态保留。

**后果 / 约束**：

- 单窗格不是逐字节原生；窗格头部继续由插件自建。原生 header 里的右栏按钮不存在，由标签条上的开关补上。
- 依赖上游 keyed slot 的 shadow 语义（同 key 不同 priority 合法，同 priority 抛错，一个子槽一个声明者）。升级 dsh 时复验 `main` 与 `RightbarRoot`。
- 卸载 shadow 后官方 `ConversationPanel` 赢回 `conversation` 格，不需要 `selectPanel(null)` 来交还主区。
- 设置页打开期间分屏仍视为 active，引用保留，避免回来时丢掉布局。

## ADR-0015 — 标签条使用原生右侧栏工具图标

**背景**：ADR-0014 在标签条放了一个文字开关「右栏」，调用 `toggleExpanded()`。原版 dsh 打开右侧栏靠的是引导页上的工具图标（文件、浏览器、终端等），每个图标打开自己的页面；header 角落里的展开图标只在右栏收起时出现。

**取代关系**：本 ADR 只取代 **ADR-0014 决策 3** 的文字开关。ADR-0014 的 shadow、`mainView` 跟随焦点、以及不自建右栏，继续有效。

**决策**：

1. **工具图标来自 `ctx.sidebarRightTabs.guide()`**，按注册表顺序画在标签条滚动区外。点击调用 `ctx.sidebarRight.openTab(kind)`，与引导卡片相同：展开右栏并打开该页。图标组件用注册项自己的 `icon`，不另画一套。
2. **展开图标只在右栏收起时出现**，调用 `toggleExpanded()`。右栏已经展开时，收起仍由右栏自己的折叠按钮负责。
3. **两个服务都可选**，都不进顶层 `inject`。缺 `sidebarRight` 时整组不渲染；缺注册表时只留展开图标。

**后果 / 约束**：

- 图标集合随已安装的右栏插件变化，本插件不写死文件/浏览器/终端名单。
- `guide()` 没有独立的“当前页”订阅；图标不标出哪一个正开着。展开与否仍只在每次 `emit` 时读 `isExpanded()`。

## ADR-0016 — 清单读取收成一个只读视图，就绪口径统一为一条

**背景**：插件对 dsh 的两份清单（`sessions.list`、`workspaces.list`）与实时状态映射的解析散在十个 module 里。同一件事写了多份、写法还互不相同：

- 「工作区成员会话」5 份，「`blank` 即未开始」5 份，「`mainView` 推导当前会话」2 份（`terminal-shell.js` 那份还多一个「取第一个 `byId`」兜底），「`byId[id]` 行查找」8 份；
- `phase` 就绪判定 6 处，分成两派：缺 `phase` 一派算就绪、一派算未就绪；相邻两个函数对 `pending` 也给出相反答案（`workspaceRunningCount` 当就绪，`projectWorkspaceSection` 当未就绪）。

注释层面也有三个 module 各自声称「上游形状的唯一适配处」。升级 dsh 时没有一处能回答「改这个字段会影响谁」。

**决策**：

1. **`catalog.js` 是唯一的解析处**。它把两份清单与状态映射读成一个**只读视图**，对外只回答领域问题：这段会话叫什么、属于哪个工作区、是否已开始、是否已归档、当前会话是谁、四个状态信号、两份清单是否就绪。其余 module 不再出现 `byId`、`sessionIds`、`phase`、`retainedBy`。
2. **纯视图，带单槽 memo**：`openCatalog({ sessions, workspaces, statuses })` 无订阅、无生命周期、不碰 `ctx`；同一组快照永远返回同一个对象（视图可以把它放进依赖数组）。`readCatalogs(ctx)` 是唯一知道客户端服务名的函数。
3. **就绪口径只有一条**（`phaseReady`）：缺 `phase` 算就绪（测试替身的形状），`pending` / `loading` 都不算，其余非 `ready` 也不算。`sessionsReady()` / `workspacesReady()` 分开暴露，`complete()` 表示两者都就绪——**只有 `complete()` 为真时，才允许把「目录里没有这个会话」当成会话已消失**（恢复修剪、冷启动落地）。
4. **只连接、不过滤**：`sessionsOf(workspaceId)` 只跳过目录里无法解析的会话；已归档与未开始的行照常返回并带上标记，因为各调用方的谓词本来就不同（`/resume` 故意列出已归档行交给列表构建器过滤，侧栏必须排除）。
5. **状态合并进信号**：`signal(id)` 的 `running` 是「实时状态或摘要行任一说在跑」，`started` 只来自摘要行（`blank` 取反，宽容地按 `blank !== true` 读），`waiting` 来自 `pendingInteraction`，`unread` 来自 `completionUnread`。五态灯的**规则**仍留在 `workspace-status.js`，只吃这几个信号。
6. **动作留在原处**：`dsh-sessions.js`（创建 / 揭示 / fork / 历史分页）与 `dsh-workspaces.js`（创建 / 删除 / 排序 / 选目录）保留「动作适配」的角色，注释改为指向 catalog。

**后果 / 约束**：

- 两处可见行为变化：两次清单都未就绪时，删除工作区的二次确认里「N 个正在运行」显示 0（安全方向）；恢复布局时，只存在于别的 `sessionIds` 里的会话会被修剪（与 ADR-0005「树里只装本工作区的会话」一致）。
- `workspace.createdAt` 被显式承认为契约字段，由 catalog 解析成数字后再参与冷启动兜底（见 `docs/upstream-contracts.md#workspace-catalog`）。
- 接口按需增长：只有出现真实调用方才加查询（例如子代理会话的 `subagent` 位、终端默认 shell 用的 `sessionIds()`），不为对称预先造接口。
- 新增读取路径时**先问 catalog**；需要**动作**或**订阅**时才另开 module。跨工作区同屏、纵向分割等 ADR-0005 / 0006 / 0009 的约束不因本决策改变。

## ADR-0017 — 窗格控制器按状态持有者切开，布局事务留在内核

**背景**：`dsh-pane-host.js` 一个文件 2228 行，`createPaneController` 返回的 face 有 **41 个成员**。调研报告把问题写成「四个角色接口（layout / workspaces / conversations / panel）」，并据此提出候选 2。真正动手前把 41 个成员逐个映射到「调用方、触及的闭包状态、是否上游强约束」之后，事实与报告的表述不同：

- 41 个成员**全部有真实调用方**，没有死面子；所以这**不是浅模块**，杠杆本来就高。问题是**不相干的状态挤在同一个闭包里**（布局簿、面板引用保留、关闭流、工作区生命周期、右栏、上游订阅），而不是「接口太宽」本身。
- **16 个布局变更成员共用同一个事务接缝**：`apply()` 写 `book` + `refs` + `snapshot`，`reconcileAll()` 写 `routingDepth`，`emit()` 是唯一的快照写入口。这 16 个入口不是 16 份状态，是同一次事务的入口——报告里「按角色切成四份」在布局这一块**无法按原样兑现**。
- 真正独立的状态只有三处：右栏的服务对与工具注册表、关闭确认的三个字段、窗格上限与在途预留。
- 没有任何成员名由 dsh 强制要求：控制器从未交给 dsh，只交出插件自定义的 `paneCommands` / `workspacePanes` 两个鸭子类型面和三个 React 组件。

**决策**：

1. **一个事务 + N 个状态持有者 + 一个聚合快照**。内核（`dsh-pane-host.js`）保留布局簿、面板引用保留、唯一的 `apply()` 事务，以及快照的冻结与广播。持有者各有自己的寄存器，通过 `snapshotPatch()` 把**自己拥有的字段**上报；`emit()` 在调用方补丁**之后**合并这些字段，所以任何调用方都无法声明一个持有者并不持有的状态（右栏的 `rightbar*`、关闭流的 `pendingClose`/`closeBusy`/`closeError`、上限的 `maxPanes`/`maxPanesError` 都是这样）。
2. **面与模块不是一一对应**。面回答「这个消费方需要看到什么」，模块回答「谁拥有什么状态」。`pane-layout.js` 一个模块出两个面：`layout`（树操作）与 `view`（对话/轨迹切换），因为 `pane-view.js` 对二者的使用是两件事，而它们背后是同一份 `book`。
3. **布局事务不切**。`apply` / `reconcileAll` / `refs` 留在内核，四个操作模块都是它的调用方，依赖单向。切它必然造出两个共享 `book` 的模块——那是假接缝。
4. **工作区生命周期故意留在内核**。它看起来像第四个持有者，实际是**建立在事务之上的启动策略**：需要内核的 18 个事务回调与 4 个上游服务。搬出去会得到一个 18 键的依赖对象，即第二个中枢——正是本决策要消除的东西。它在内核里，但**不是** face 的成员缺陷：它对外只暴露 7 个成员。
5. **消费侧必须跟着窄**。`index.js` 把五个持有者/面分别交给需要的模块：`paneCommands` 拿 `layout` 与 `budget`，侧栏拿 `workspaces` 的相关成员，设置页只拿 `budget.setMaxPanes`。
6. **不为凑行数而切**。600 行上限适用于新模块；有状态簿的模块允许例外，本次内核被例外覆盖（见后果）。

**后果 / 约束**：

- face 从 **41 键降到 18 键**（13 个自有成员 + 5 个持有者/面）。`dsh-pane-host.js` 从 2228 行降到 1506 行，新增 `pane-panel.js`（191 行 / 4 成员）、`pane-layout.js`（249 行 / 9 + 4 成员），`pane-close.js` 从 166 振到 222 行（多了自己的 face），`pane-budget.js` 从 178 到 609 行（多了创建策略）。
- **未达成的验收条件**：内核 1506 行，远超 600 行上限，也超出最初给「事务文件」留的 900 行例外。要压到 900 以下只能做第 4 条已拒绝的工作区生命周期搬迁。也就是说：**接口变深了，文件没有变短**；把行数当验收口径会诱导假接缝。`pane-budget.js` 609 行，超出 600 行 1.5%，已明确接受。
- `layout` 面是 **9 个成员**而不是 8：`focusedWorkspaceId` 的回退行为（空工作区仍报出宿主列表里的第一个工作区，让 `/clear` 能开出首个窗格）有测试钉住，为凑数字删掉会删掉被测行为。
- 删除 `currentReference()`：非测试代码零调用方，`paneReference(focusedPane().paneId)` 表达同一件事。`reactivate()` 保留，但没有生产调用方：shadow 让原生 reveal 不再卸载分屏，所以它可能永远不被调用。它留下是因为它是**唯一可执行的「重新 reconcile 是幂等的」这句话**——`workspace-layout.test.js` 用它钉住「再 reconcile 一次不移动引用、不移动唯一的 `mainView`、不调 `selectPanel`」。删掉它，这条不变量就只剩注释。
- 两个持有者带自己的测试：`pane-panel.test.js`、`pane-close.test.js`、`pane-layout.test.js`（新增 39 个用例：面板 9、关闭流 11、布局 10、预算 9）；内核那 2000 行整根测试不动——它们断言的是服务调用（`retain` / `create` / `interrupt`），与实现位置无关，按模块重写买不到新信息。

## ADR-0018 — 关闭窗格后同一排重新均分宽度

**背景**：真机验证时报「关掉中间窗格，后两格的宽度会合并，而不是重新均分」。查证后的机制是 `layoutTree.close()` 只做结构崩缩——兄弟子树提升到父节点的位置——**不调用** `equalizeRowRatios`；只有 `split()` 会调用它。这条规则不是意外，而是被记录过的：ADR-0011 决策 2 写着「关闭窗格仍只提升兄弟子树，不重新均分」，ADR-0011 的后果与 ADR-0006 的后果各写了一遍，代码注释与 GLOSSARY 又各复制了一份。

实测（纯横排三等分）：

| 操作 | 结果 |
| :--- | :--- |
| 关最左 | 1/2 · 1/2 ✅ 看起来是对的 |
| 关中间 | 1/3 · 2/3 ❌ |
| 关最右 | 1/3 · 2/3 ❌ |

也就是说旧规则的真正含义是「被关掉的是父节点的第一个子节点时才像均分」。只有关最左是对的，所以这个不对称一直没被注意到。

**取代关系**：本 ADR 取代 **ADR-0011 决策 2** 的第二句（「关闭窗格仍只提升兄弟子树，不重新均分」）、**ADR-0011 后果** 的第一条，以及 **ADR-0006 后果** 第一条中「关闭窗格仍沿用兄弟子树提升，不会重新均分」这半句。ADR-0011 的其余决策（新建后按窗格数均分、拖拽比例让位、纵向分割不参与、比例地板）继续有效。

**决策**：

1. **`close()` 之后对整棵树跑 `equalizeRowRatios`**，与 `split()` 是同一个函数、同一条规则。纯横排关闭任一格后恒为 `1 / 剩余窗格数`。
2. **列（`col`）自身的比例仍然不动**，但外层 `row` 按「该列**剩余**窗格数 / 总窗格数」重新分配份额。因此在列里关掉一格会让那一列变窄（实测 `row(row(p1,p4), col(p2,p3))` 关掉列内 `p3` 后，外层比例从 1/2 变 2/3）。这是「一律均分」的直接代价，已知并接受；替代方案（只在父节点是 `row` 时均分）能避免它，但会让「关中间」和「关列内」走两套规则。
3. **拖拽比例不因关闭而保留**：与 `split()` 已有的行为一致（横向新建也会丢掉拖出的横向比例）。不为「这一排是否被拖过」在布局里引入新的状态位——它会成为需要持久化、需要迁移的第四种状态。
4. **实现位置在纯模块里**：规则写在 `layout-tree.js:close()`，不是内核补一步。`close` 与 `split` 是同一结构变换的两端，规则放在一起才不会被下一次改动拆散。

**后果 / 约束**：

- 关闭后不再出现「2/3 宽的残格」。用户手动拖过的横向比例会在关闭时被抹掉，分隔条只在「下一次添加/关闭之前」有效。
- **不影响恢复路径**：修剪与恢复走 `layout-store.js:pruneToKnownSessions` → `normalizeLayout`，不经过 `close()`，所以已保存布局里残留的 `1/3 + 2/3` 不会被静默改写；它会在用户下一次关闭或新建那一排时自然收敛。不需要数据迁移。
- 关闭到只剩一格或零格时行为不变（`equalizeRowRatios` 对叶子与 `null` 是恒等的）。
- 钉住该规则的三条测试在 `layout-tree.test.js`：等宽三格关中间/关最右都留下 1/2、拖拽过的排关闭后被抹平、列内关闭会改变外层份额。

## ADR-0019 — 进行中的对话不被旧对话抢走

**背景**：对话进行中，焦点会自己跳到一段已经结束的旧对话。三条路径都会造成这个结果：

1. dsh 用「仍有 `mainView` 保留的会话」推导当前会话，而且一旦当前会话还有保留就不会改口。启动时恢复的旧会话常常一直握着一份 `mainView`。清单一更新，`uiSession.adapter.current` 就会落到那段旧对话上；ADR-0014 决策 4 要求窗格跟着 current 走，于是进行中的窗格被替换成旧对话。
2. 宿主重索引会话目录时，工作区成员列表会短暂漏掉正在跑的会话。修剪把这当成「会话已删除」，关掉该窗格，焦点落到旁边那段已结束的对话上。
3. 切到一个工作区时，若焦点窗格上的会话还没被标成「已开始」（`blank` 仍为真）但其实已经在跑，`focusOrOpenWorkspaceConversation` 会把它换成该工作区里最近更新的一段已开始对话，也就是更早结束的那一段。

**取代关系**：本 ADR 收窄 **ADR-0014 决策 4**。current 仍然会落到焦点窗格上，但**不能把一段正在运行的对话换成一段没有在运行的对话**。ADR-0014 的其余决策继续有效。

**决策**：

1. **运行中的焦点对话忽略空闲的 current**。`syncCurrent` 在焦点会话 `running === true`、而 shell current 指向的会话没有在运行时直接返回。两边都在运行时仍跟随，空闲对话之间的 current 切换也仍跟随。
2. **修剪保留正在运行的窗格**。成员列表暂时不含某个会话时，只要该会话仍在运行，已加载布局里的对应窗格不删。会话真正结束后，下一次清单更新再按成员列表修剪。
3. **工作区揭示不替换正在运行的焦点**。`focusOrOpenWorkspaceConversation` 看到焦点窗格的会话正在运行时，即使它还不算「已开始的工作区对话」，也不换成别的会话。

**后果 / 约束**：

- 一轮还在跑时，原生 `openSession` 若指向一段空闲旧对话，不会把焦点窗格拉走。分屏里的 `/resume`、标签和窗格点击不走这条路径，不受影响。
- 成员列表里的短暂空洞不再写成「这段对话已不存在」。会话确实结束后才会被修剪掉。
- 钉住这三条的测试：`dsh-pane-host.test.js` 的 running/idle current，`workspace-layout.test.js` 的成员空洞与未开始但正在运行的焦点。

## ADR-0020 — 插件重挂载恢复自己的视图，不跟随旧的原生 current

**背景**：ADR-0019 修掉了进行中的对话被空闲 current 抢走的三条路径，但没有覆盖**插件重挂载**。开发插件时热重载会先 teardown 旧 fiber、再 import 新 bundle（`dsh-client-hmr` → `client-modules` 的 `replace`），于是新建一个窗格控制器。旧控制器持有的 `mainView` 在 teardown 时释放，而 dsh 的 `uiSession.current` 仍钉在原生选区上（`publishMain` 在旧 current 还持有 `mainView` 时不会改口）；新控制器 `activate()` 读到的 `catalog.current()` 往往是一段更早的旧对话，随后用它替换焦点窗格，进行中的对话就跳走了。第二个缺口是可见工作区没有被记住：控制器只能从 `catalog.current()` 反推工作区，跨工作区时会整块切走，再在错误的工作区里落地。

**补充关系**：本 ADR 补充 **ADR-0019 决策 1** 的边界：重挂载时 current 不覆盖已恢复的焦点，运行中/空闲判定不变。ADR-0014 决策 4 继续有效：挂载完成之后，原生 current 的变化仍然跟到焦点窗格。

**决策**：

1. **先恢复自己的树**。`activate()` 不带 session 时，先按记住的可见工作区恢复该工作区的布局；焦点窗格里已有会话时，焦点就是目标，`catalog.current()` 只在该工作区没有已恢复窗格时兜底。即使没有可见工作区提示（升级后的第一次运行），只要兜底选中的工作区里有已恢复的焦点窗格，也保留它。
2. **记住可见工作区**。新增插件自有键 `dsh.hkcraft.active-workspace.v1`（`layout-store.js`），在 `setActiveWorkspace` 时写入。它只是提示：读取时先对照目录验证，目录已就绪而工作区不存在则忽略，并在启动落地时连同它的布局键一起清掉；存储不可用或损坏时退化为“没有提示”。
3. **启动落地保留恢复的焦点**。`settleBootWorkspace` 在树已恢复且仍有焦点窗格时直接落地，不再用 `focusOrOpenWorkspaceConversation` 把空白/空闲的焦点换成该工作区最近的旧对话；只有窗格被修剪掉之后才回到原来的落地逻辑。
4. **不引入新的选择语义**。原生 reveal / `openSession` 在挂载之后仍然通过 `syncCurrent` 落到焦点窗格；“运行中的焦点忽略空闲 current”的规则不变。

**后果 / 约束**：

- 重启或插件热重载显示的是分屏最后一次呈现的工作区、树与焦点，而不是 dsh 原生选区；这与 ADR-0014 “刷新或重启后恢复树形、比例、焦点与视图”一致。
- 新增一个 localStorage 键；它与布局键一样是插件自有存储，dsh 不读不写。
- 升级后第一次运行可能还没有提示键：同工作区的焦点仍能恢复，跨工作区仍按旧逻辑选择，下一次切换/激活后写入提示。
- 钉住该行为的测试：`workspace-layout.test.js` 的两条 reload 用例、无提示恢复、空白对话恢复、失效工作区清理；`layout-store.test.js` 的提示读写与容错。
